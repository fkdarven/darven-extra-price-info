# 4.0.0 stabilization design — Darven Preços Parcelados

**Status:** proposed  
**Date:** 2026-07-31  
**Branch:** `codex/4.0.0-darven-precos-parcelados`

## Context

The 4.0.0 refactor introduced normalized settings, React administration,
accessible public installment dialogs, translations, and WordPress.org assets.
Focused QA caught two release-package/persistence defects and the resulting
release ZIP is structurally clean. The whole-branch review then identified
seven functional gaps that invalidate a polished release: dynamic YITH mode
can change on an unrelated save, Display controls are inert, translations do
not load completely, variable-product behavior is incomplete, modal IDs can
collide after AJAX, a save can discard in-flight edits, and the public readme
describes an obsolete UI.

The maintainer explicitly chose stabilization without cutting features. This
design therefore completes the advertised capabilities rather than hiding or
removing them.

## Goals

- Preserve the technical slug, namespace, update path, legacy option keys,
  legacy product metadata, and pre-save behavior of 3.3.1 installations.
- Make every visible 4.0.0 setting effective in the storefront or product
  behavior it claims to control.
- Make PHP and JavaScript `pt_BR` translations load from the distributable
  package.
- Keep the React UI usable, accessible, and safe under slow REST saves.
- Ship a WordPress.org package and documentation that accurately describe the
  plugin and exclude development-only material.
- Demonstrate the result with focused regression tests, real release ZIP QA,
  PHP 8.0 and WordPress 5.0 runtime checks when those environments are made
  available, and a fresh whole-branch review.

## Non-goals

- No new pricing formula, payment provider, public plugin slug, or namespace.
- No destructive migration: legacy options and product meta remain mirrors and
  direct variation-level data, when present, keeps precedence.
- No release, tag, SVN operation, or public publishing as part of this work.

## Considered approaches

1. **Stabilize all advertised behavior (selected).** Repair each review
   finding, add regression coverage at the persistence/render/package
   boundaries, then repeat release QA. This costs a focused stabilization
   cycle but fulfils the approved 4.0.0 feature set.
2. **Hide or remove incomplete controls.** This would reduce immediate work,
   but would make the release smaller than the agreed React/translation scope
   and leave users without the promised configuration capability.
3. **Release a narrow compatibility version and defer 4.0.0.** This lowers
   short-term release risk but throws away the completed refactor and delays
   the new UI. It is unnecessary once the identified contracts are corrected.

The selected approach is (1).

## Design

### 1. Settings contracts and compatibility

`SettingsRepository` remains the single normalizer for settings data. Its
normalized compatibility document must always materialize
`darven_epi_yith_dynamic_pricing_mode` as either `auto` or `disabled`.

- A new installation and legacy configuration explicitly marked as dynamic
  pricing use `auto`.
- A legacy configuration explicitly unmarked uses `disabled`.
- A React GET followed by an unchanged PUT must round-trip to the same
  effective YITH mode; merely opening/saving another setting must not alter
  price selection.

The REST permission callback must establish capability before differentiating
an invalid product ID from an editable product. The handler may produce a
404 only after authorization is established.

The no-JavaScript admin path is a compatibility requirement: settings and
product controls receive server-rendered classic controls inside a `<noscript>`
or equivalent fallback path, submitting through the existing sanitizers and
classic WooCommerce save flow. React mounts only when JavaScript is available.

### 2. Effective Display settings

Display settings remain stored in the normalized document and legacy mirrors.
`Frontend\Assets` enqueues the static public stylesheet, then obtains the
sanitized effective settings and adds generated CSS through
`wp_add_inline_style()` on that same handle. `InlineStyles` remains the
single generator; it must have a production call site.

The generated CSS only uses the existing allowlisted colors, font sizes and
selectors. No raw option value becomes CSS. A save-to-storefront test proves
that a changed control produces the expected inline declaration.

### 3. Product and modal behavior

`ProductSettingsRepository` resolves settings in this order:

1. explicit settings directly on a variation;
2. settings from the variable parent when the variation has no direct
   relevant setting;
3. normal product defaults.

The effective settings control visibility flags only; the variation object
continues to supply its own price calculation. This preserves direct legacy
variation configuration while making the parent UI work after a customer
selects a variation.

Each public dialog receives a server-generated `wp_generate_uuid4()` based
identifier rather than a per-request counter. Frontend JavaScript resolves
dialog controls inside the nearest installment component rather than through
a global document lookup. Two fragments rendered in separate PHP requests can
therefore coexist without duplicate IDs or opening the wrong dialog.

### 4. React interaction and accessibility

While a settings PUT is pending, the whole editable region is disabled and
marked busy; not only the save button. The response is applied only after
that immutable pending state ends, preventing a concurrent edit from being
silently overwritten.

Tabs retain their current visual design but implement the WAI-ARIA tabs
keyboard contract: one roving tab stop, arrow navigation, Home/End, selected
tab focus, correct `aria-selected`/`aria-controls`, and keyboard tests. Admin
styles register their shipped RTL replacements with WordPress.

### 5. Translation delivery

PHP loads translations from the plugin-relative `languages/` directory using
the plugin basename. The source language is English: metadata and msgids are
English, while `pt_BR` is the delivered translation.

The build/release workflow creates JavaScript catalogs whose names match the
actual built script handles or bundle hashes consumed by
`wp_set_script_translations()`. The release package contains the matching MO
and JSON catalogues, not stale source-path-only JSON files. The PO is completed
for all user-facing settings, including YITH explanation, typography labels
and position ordering; the POT is regenerated from the final English source.

Tests exercise both real PHP domain loading and JavaScript translation file
resolution for the current assets.

### 6. Release material and package hygiene

`readme.txt` describes the current three screenshots: React settings, Darven
product tab, and accessible installment dialog. Its FAQ, compatibility notice
and changelog use the new UI terminology. The obsolete fourth caption is
removed.

The release builder continues excluding source tests and additionally excludes
obsolete `i18n/` catalogs for the retired domain. Release assertions reject
test files, stale catalogues, local configuration, symlinks and WordPress.org
asset staging while requiring current built assets, translations, headers and
a single 4.0.0 version.

## Testing and acceptance

Each defect is reproduced before its fix and receives a focused regression
test. The stabilization is accepted only when:

- YITH mode round-trips correctly for fresh, legacy-auto and legacy-disabled
  settings; unauthorised product REST requests do not expose existence.
- Every Display control has an observable, sanitized storefront result.
- Parent and direct variation settings behave correctly in `price_html`.
- Separate AJAX fragments have unique dialogs and retain keyboard/focus
  behavior.
- A pending settings save cannot discard a later user edit, and tabs work by
  keyboard.
- `pt_BR` strings load for PHP and both React bundles; no functional PO entry
  is left blank.
- Classic admin fallback, RTL admin styles, readme screenshots and package
  exclusions work as documented.
- Full PHP, JavaScript, build, package and local clean/upgrade QA pass on the
  actual ZIP. PHP 8.0 and WordPress 5.0 must be executed before release, or a
  maintainer must explicitly accept each missing environment as a release
  exception.

## Risks and mitigations

- **Legacy semantic ambiguity:** fixture tests define every inferred YITH
  state before changing normalisation.
- **CSS injection risk:** only pre-existing sanitized values enter the inline
  stylesheet generator.
- **Variation regressions:** direct variation metadata wins before parent
  fallback and price math remains attached to the variation object.
- **Translation drift:** catalogs are generated as part of the asset/release
  flow and validated against actual bundle hashes.
- **Release pressure:** the human publication gate remains closed until the
  acceptance matrix and fresh review are complete.
